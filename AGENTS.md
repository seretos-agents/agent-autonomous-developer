# agent-autonomous-developer

Pure skill + agents plugin (no binary, no MCP). Takes **one work package** — a ticket, or an epic standing for all its child tickets — from a prepared worktree to a pull request with a **green CI pipeline**, for projects in any language (stack auto-detected), on top of the `agent-project-issues` MCP.

README.md covers *what* it does, install, and release. The skill and the agents document their own rules. This file records only the non-obvious decisions a contributor must not silently break — the cross-file invariants and the rationale you cannot reconstruct from any single file.

## Tool priority

Skills and MCP tools take priority over raw file tools — and this **explicitly overrides** the generic harness default that says "prefer the dedicated file/search tools (Glob/Grep/Read)". When a skill or MCP tool covers the task, reach for it first; fall back to raw Glob/Grep/Read only when none applies.

## Scope: one package in, one green PR out — nothing above that

This plugin has exactly one skill, `process-developer`, and it is not model-invocable: the caller is a headless `claude -p` session started by an orchestrator (in the Seretos ecosystem, `agent-ticket-orchestrator`), or a human typing the slash command in a worktree. The plugin knows **nothing** about boards, ticket selection, bundling, worktree lifecycle, or other packages. It used to carry a fleet layer (`orchestrate-tickets`, wave scheduling, a `dispatch` lane router, a `conflict-analyst`); all of that moved up and out in the 2026-08 rebuild, for a reason that is still load-bearing: parallelism inside one repository bought nothing and cost the entire B6 liveness apparatus, while a lower plugin that knows about the board cannot be reused by a caller with a different board. Do not add ticket selection, column writes, or multi-package logic here.

The skill was named `process-ticket` until ticket #126; it was renamed so the two lower plugins have symmetrical entries (`process-developer` here, `process-prompt-engineer` in `agent-autonomous-prompt-engineer`). Every incident narrated in this file under the new name happened under the old one — search tickets, PR titles and commit subjects before #126 for `process-ticket`. There is deliberately no alias: the caller switches in the same release window.

## The contract with the caller is a write obligation, not a return schema

A headless dispatch returns "process ended" plus text. That channel is structurally too poor to carry state, and a caller that reconstructs state from prose is a bug waiting to happen. So `process-developer` owes the caller a **fixed set of comment events** on the package ticket (`<!-- adev:event v1 … -->`, names and fields in `skills/process-developer/SKILL.md` → "Events"). The block is produced only by `scripts/event_block.py`, whose stdout the skill posts unchanged; the model never composes it. A deterministic external parser (`ecosystem-statistics`) reads the block, and hand-built blocks reached tickets in three shapes (raw, fenced, HTML-escaped), with four or five gates and a trailing space after an empty `pr:` (#134). The caller derives everything from the latest event. Three invariants follow:

- The event vocabulary is **closed**. Adding an event is a contract change: it also goes into the renderer's `EVENTS` tuple (a gate into its `GATES` tuple), and the caller's maintainers must be told (`agent-ticket-orchestrator/AGENTS.md` carries the same table). `replan-triggered` (2026-08-25) is the one addition since the vocabulary was fixed — additive and non-terminal, see "Round caps are progress-based, not just round-counted" below.
- Exactly **one terminal event** per run (`ci-green`, `blocked`, `failed`), posted last, then the turn ends. A run that keeps working after a terminal event makes the caller act on a stale state. `replan-triggered` is the deliberate exception: it is non-terminal by design, and more work in the same turn is expected to follow it.
- The `rounds:` line must distinguish findings rounds (`f`) from infrastructure rounds (`i`). A human who reads a `failed` event has to be able to tell "three real critiques" from "three crashes" — they are different problems with different fixes. It also now carries `generation:` alongside it (see below).

## Phase 0 orients on the branch instead of taking a parameter

A retry can arrive on a branch in two different states — one where the previous
attempt crashed mid-pipeline, and one where the previous attempt finished, got
reviewed, opened a PR and went CI-green, but the merge failed because the base
moved underneath it. Those two need opposite treatment: the first needs the
whole pipeline again, the second needs only a rebase. `process-developer` tells
them apart itself, from facts, in `skills/process-developer/SKILL.md`'s Phase 0 —
**deliberately not from a parameter the caller sets.** The caller (this
ecosystem's `agent-ticket-orchestrator`) cannot reliably distinguish "crashed"
from "finished but conflicted" without duplicating this skill's own state
machine; the discriminator this skill actually has is cheap and exact: *an
open PR for this branch's head, with every CI run on the exact current HEAD
green,* since this pipeline never opens a PR before Phase 4 (review) approves.
Anything less finished than that is a resumed crash, not a resumed conflict,
and gets the full pipeline. This also means `agent-ticket-orchestrator`'s
retry dispatch is byte-identical whether it is retrying a crash or retrying a
conflict — see its `AGENTS.md`, "Merge outcomes are classified, and a conflict
is a retry".

No new event exists for the repair path (Phase R). The vocabulary stays
**closed** — Phase R posts the same events Phases 1–6 could always post, just
fewer of them, and advances the fifth gate, `rebase=`, on the existing
`rounds:` line rather than a new event. A caller that ignores the gate loses
nothing, but the `rounds:` line is not opaque: an external parser reads it,
which is why the renderer always prints all five gates.

**One branch has at most one open PR, ever.** Phase 0 looks up any existing
open PR for its head before doing anything else, and Phase 5 reuses it
(`update_pr`) instead of calling `create_pr` a second time. This was a latent
bug independent of the conflict-retry feature: before this change, a second
attempt on the same branch called `create_pr` unconditionally and would have
either duplicated the PR or errored, silently, the first time any retry
reached Phase 5 with a PR already open.

## There is no human in this process, by construction

The dispatching CLI passes `--disallowedTools AskUserQuestion`, and no agent definition here grants it. A question is a **`blocked` event** and the end of the run. Before posting one, `process-developer` must have tried to answer from the package transcript (epic body, sibling tickets, prior comments, the code the planner cites) and must say in the event what it checked and why that was not enough — escalating is not forwarding. The human is asked for a **decision**, never for a **retry**: anything whose answer would be "try again" is covered by the round caps. A `blocked` event whose only sensible reaction is "kick it again" is a bug in this plugin.

## Every Agent dispatch is unnamed, synchronous, fresh

A named `Agent(...)` spawn delivers on a `SendMessage` mailbox nothing here listens to; the caller waits for a task-notification that never comes (`#60`, `#88`). Resuming an existing agent via `SendMessage` is the same channel by another name. Every round trip — planner answer rounds, critic rounds, developer fix rounds, re-reviews, CI repairs — is a **fresh unnamed `Agent(..., run_in_background: false)` call with everything re-inlined**: plan, findings, and — since ticket #105 — **only the current round's** change report, not the whole accumulated chain (see "The plan-critic loop converges on a threshold, not on zero" below for why that changed). Subagents cannot refetch. The same rule is ecosystem-wide (root `AGENTS.md`); this plugin is where it was learned.

The same non-suspension applies one level down, inside a single developer dispatch: a subagent that ends its turn while it backgrounded a shell command does not get suspended and later resumed either — the harness kills the background process and the turn's "I'll resume once it completes" is never honored (ticket `#93`, a live recurrence of the exact failure mode `#83`/`#88` already fixed at the fleet layer, this time inside a single dispatch). `agents/developer.md`'s prose Hard Rule forbidding this was already in place when `#93` happened — a live incident proved prose alone is not reliable enough — so it got a mechanical backstop: the `SubagentStop` hook `hooks/check-developer-background-wait.mjs` (wired in `hooks/hooks.json`, matcher `developer`) scans the developer's own transcript for a backgrounded `Bash` call and blocks the stop.

## Nothing runs in the background — not even with a `Monitor` (ticket #101)

Until 2026-08-26 the rule above had a sanctioned escape: background the full suite (`nohup … &`) and wait for it **in-turn** with the `Monitor` tool, which the two turn-end hooks accepted as "resolved". `agents/developer.md` even *mandated* that shape for every full-suite run, on the theory that the foreground `Bash` timeout (10 min) is shorter than real suites. `agent-worktree#176` killed that theory twice in one day: attempt 1 backgrounded the suite, armed a `Monitor`, wrote *"Nothing more to do until that fires"* and ended its turn — the hooks saw the `Monitor` and let the stop through, and nothing ever fired, because nothing wakes a headless process; attempt 2 backgrounded a suite with a hanging test and was killed by the harness's 600 s ceiling with the hang's diagnostics inside it. Both sessions had a project `AGENTS.md` in front of them that said *never background the suite* in so many words; the plugin's own instruction said the opposite, louder, and won. Between `#93` (2026-08-23, "backgrounding the verification run is a bug") and `#176` the mandatory-background paragraph had crept back into `developer.md` through a later ticket — which is why this rule now has a doc regression test (`tests/test_no_background_rule.py`), not just prose.

The rule is now absolute and lives in three places that must agree: `agents/developer.md` (step 4 + Hard Rules), `agents/reviewer.md` (Hard Rules), `skills/process-developer/SKILL.md` ("Turn-end discipline"). **No test run, build or wait is ever started with `run_in_background: true`, `nohup … &`, `Start-Job`, `Start-Process` or `Monitor`.** A suite that does not fit one call runs as synchronous chunks, one foreground `Bash` call each with an explicit `timeout` (max 600 000 ms), the project `AGENTS.md`'s chunks if it names any. The one permitted wait is the foreground `scripts/ci-wait-pipeline.sh` (`project-issues wait-pipeline`) call of Phase 6 (see "CI is the verdict" below): a blocking call inside the turn, with a tool `timeout` above its own `--timeout`, not an exception to the absolute rule. A chunk that hits its timeout is *information* — re-run it with a per-test timeout that dumps stacks (`pytest --timeout=<n> --timeout-method=thread` or the project's equivalent) and carry the dump into the change report and the `failed` event; those stacks are exactly what `#176` never produced. There is no legitimate exception; a case that seems to need one is a `blocked` event.

Mechanically, three hooks in `hooks/hooks.json` enforce it, all sharing one classifier (`backgroundReasonForToolUse` in `hooks/lib/turn-end-scan.mjs`, dispatching to `backgroundReasonForBash` for `Bash` — `run_in_background: true`, `nohup`, `Start-Job`, `Start-Process`, trailing `&`): the `PreToolUse` hook `hooks/check-no-background.mjs` (matcher `Bash|Monitor|Agent`) refuses the call before it runs, exit 2 with the reason on stderr; the `SubagentStop` (`#93`) and `Stop` (`#23`) hooks are the backstop behind it and block a turn ending with a backgrounded command outstanding. Since `#101` a `Monitor` call resolves **nothing** in that walk — the only thing that does is the PreToolUse refusal itself, recognised by the `[adev-no-background]` marker it leaves in the transcript, so a refused call cannot trap the agent behind a stop it has no way to satisfy. **Keep the classifier, the prose rule, the doc test and the hook scope gate in sync**: the PreToolUse hook fires in every session that loads this plugin, so it is scoped like the `Stop` hook (presence of `<cwd>/.adev/`) **or** to one of this plugin's own `agent_type`s; a human's interactive session keeps `Monitor`. To exercise it by hand: `mkdir .adev` in any directory and run `claude -p` there with a prompt that tries a backgrounded command.

**Ticket #139 extended the same classifier to a backgrounded `Agent` dispatch.** The `Agent` tool's own schema backgrounds by default ("Agents run in the background by default … Set to false only when your very next action depends on this agent's result"), so a call with no `run_in_background` key, or any value other than `false`, is exactly the shape `backgroundReasonForToolUse` already refused for `Bash(run_in_background: true)` — a long developer/reviewer/critic dispatch (see "Every Agent dispatch is unnamed, synchronous, fresh" above) silently killed at the harness's background-task ceiling, with no event ever posted. Only an explicit `run_in_background: false` is a foreground dispatch. `describeToolUse` (same file) labels a refused/unresolved `Agent` call as `Agent(<subagent_type ?? description>)` for the refusal text and the block reason, since a bare command string means nothing for a subagent dispatch. The Unity MCP bridge's own cold-boot poll is unrelated and out of scope for this ticket.

And it applies one level *up* as well, to the top-level session: headless (`claude -p`) there is no loop that wakes the session after its turn ends, so **the session ending its turn ends the process** (ticket `#23`). This was measured, not assumed — `lib-python-worktree` #140 was run three times with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` unset (default 600 s), at `0`, and at `7200000`, and died the same way each time; `0` in particular means *no* wait, not "wait indefinitely" as the harness's own hint line claims. The env var sets how long the process loiters before it is killed; it never turns waiting into resuming, so **do not "fix" #23 by setting it**. The backstop is the `Stop` hook `hooks/check-session-turn-end.mjs`, wired in `hooks/hooks.json` without a matcher, which blocks the stop on two conditions: an outstanding backgrounded `Bash` call (same detection as the `#93` hook — the walk is shared in `hooks/lib/turn-end-scan.mjs`, change it in one place and both levels move together; since `#101` a `Monitor` no longer counts as resolving it), and a worktree holding changes or commits that no remote has. The second condition is the one that pays: the caller prescribes `worktree_remove` after a failed second attempt, so unpushed work is destroyed and the retry re-pays for context, planning and critique (`#22`; on #140 it was 1979 insertions across 15 files, on #139 the same loss had already happened and was recovered by hand as a patch). It is scoped by the presence of `<cwd>/.adev/` — a `Stop` hook otherwise fires in every session that loads this plugin, including a human's — and capped at one block per turn via `stop_hook_active`. **Keep the scope gate and precondition 4 in sync**: if `process-developer` stops creating `<worktree_path>/.adev/<package>-<attempt>/`, or the caller stops starting the session with cwd = the worktree, the hook silently stops firing.

## Checkpoints fire at every tree-changing step, not just turn end (#115); the plan and findings are handed on by path, not pasted (#113)

Before #115, only the turn-end rule above (`SKILL.md`, "Turn-end discipline") committed and pushed — an external hard kill (a cost-limit kill, not a graceful stop) mid-pipeline lost everything since the last turn boundary, which on a long package can be the whole attempt so far. The fix is not a new mechanism, it is the *same* commit+push logic, named once as `skills/process-developer/SKILL.md`'s `### Checkpoint (commit + push)` procedure, and fired at every point that changes the tree instead of only at the end: after RED (Phase 3a) and after GREEN (Phase 3b), after every Phase 4 fix round and Phase 6 CI-repair round returns, at three points inside Phase R's rebase, and at turn end. Phase 5's own push step is the one deliberate exception — it keeps its pre-existing wording verbatim because it alone must also survive a rejection caused by someone else pushing to the branch while this session worked. Three skip guards (clean tree with nothing unpushed, a rebase in progress, detached HEAD) keep the procedure from firing where it would do nothing or actively harm — in particular, checkpointing mid-rebase would swallow the staged conflict resolution Phase R step 2 hands to `rebase --continue`. A turn-end skip is the one case that must be recorded in the terminal event's text (`checkpoint skipped at turn end: <guard> …`); a mid-pipeline skip needs no note. `push_mode` (`plain`/`lease`) is named per call site, never inferred: `plain` sites push fast-forward-only; the three Phase R sites use `lease` (`--force-with-lease`) because a rebase always rewrites this branch's history relative to `origin`, and a bare `--force` is never permitted anywhere.

**#138/#140 moved the commit half into the developer's own last tool call.** Even with #115's cadence, a kill between a `developer` subagent's last `Edit`/`Write` and the orchestrator's next call still lost the files already on disk (`unity-avatar#4`), because the checkpoint could only fire once the dispatch had returned. Every `developer` dispatch now ends with `scripts/developer-commit.sh <worktree_path> <message>` (`agents/developer.md` step 6; the script is #140's, with the same skip guards in the same order as the Checkpoint's step 1), which commits locally and never pushes; each dispatch carries `ticket=<package>` for the message. The Checkpoint's commit step is now a fallback for whatever a dispatch left uncommitted and for the orchestrator's own edits. The orchestrator still does **every push** and still owns the skip guards and `push_mode`, because those depend on pipeline state the subagent does not see (whether Phase R rebased, whether Phase 5 must survive someone else's push). The Phase R conflict-resolution dispatch is the one developer dispatch that does not commit: it only stages, and `rebase --continue` makes the commit. The Phase 6 limitation below is unaffected — a developer commit is never a push.

**Known limitation, accepted for this ticket rather than redesigned:** the
Phase 6 CI-repair checkpoint (one of #115's five new call sites) pushes
immediately after the fix-round developer returns, *before* the fresh review
that follows it — deliberately, for the same reason RED tests are
checkpointed before the test critique runs: a crash during that following
review must not cost the fix. But Phase 6 runs after Phase 5 has already
opened the PR, so a crash between that push and the review's completion,
followed by CI later going green asynchronously on that exact pushed HEAD,
could make Phase 0's `finished` discriminator (open PR + all-green CI at
HEAD, see "Phase 0 orients on the branch" above) misclassify an unreviewed
CI-repair fix as reviewer-approved on the next retry, skipping Phase 4
entirely. A proper fix needs the discriminator to also confirm a
`review-verdict` approval was posted for this exact HEAD, which no current
event carries (no event carries a commit sha except `ci_run:` on `ci-green`)
— that is an event-schema change, out of scope for a ticket about checkpoint
cadence and payload size, so it is recorded here rather than attempted inline.

Ticket #113 lands in the same branch and cuts a different cost: the planner now `Write`s its own plan to `plan_path` instead of returning the full plan text on every round (its reply is now a `STATUS` line plus a `≤30`-line summary, explicitly labelled as a summary and not the plan), and both critic wrappers (`agents/plan-critic.md`, `agents/test-critic.md`) report only `finding_class == "blocking"` findings inline, four or five fields each, plus a `MERGED: <absolute path>` pointer to the full `critique-merged.json`. `process-developer` now hands the plan and the critics' findings on **by path**, `Read` by whoever receives them, everywhere it previously pasted the text in full: the planner re-dispatch on a blocking plan-critic finding, the note-class forwarding into the Phase 3 developer dispatches, and the replan dispatch's accumulated findings history across a whole generation. This is additive to the pointer-return contract already established for change reports (ticket #105, "Every Agent dispatch is unnamed, synchronous, fresh" above) — only the *current* round's evidence is ever inlined, never the whole chain. The closed 13-event vocabulary is unaffected; `agents/developer.md`/`agents/reviewer.md` stayed byte-unchanged at the time (#115 AC5; #138 later changed `developer.md`'s commit rule, not its `plan` input) since they already hold `Read` and already read whatever value their `plan` input carries — the one accepted staleness is that their own prose still describes `plan` as inlined text while the value is now a path, which `SKILL.md`'s dispatch prompt states explicitly at each call site; a prose refresh of those two files is a follow-up ticket, not a behavioural gap here.

## CI is the verdict; the local suite is a pre-filter

The developer still runs the full suite locally (synchronous foreground chunks inside its turn, never backgrounded — see `agents/developer.md` step 4 and "Nothing runs in the background" above) because it is cheaper to fix locally than on the runner. But the event for it says `tests-green` with "local pre-filter only", and the only success event is `ci-green`. Two reasons: local runs crash regularly on this platform, and a CI result was produced by nobody with a stake in the outcome — the same argument as critic isolation, applied to tests.

Waiting for the pipeline (ticket #118) is **one blocking foreground call**, `Bash("bash ${CLAUDE_PLUGIN_ROOT}/scripts/ci-wait-pipeline.sh --project <id> --sha <head> --timeout 540", timeout: 600000)`, in **`process-developer`'s own turn**, never inside a subagent: a subagent's background processes die with its turn and its task-notifications go to the parent, which is exactly the silent stall `#88` documented. The installed Claude Code refuses a standalone `sleep <n>` and this plugin forbids `Monitor` and background jobs, so the old `list_pipeline_runs` + sleep ladder had no permitted form; the CLI does the sleeping inside its own process, and the tool `timeout` (600 000 ms, the Bash ceiling) outlives the CLI's 540 s so the CLI always ends first. It is a blocking foreground call, not a backgrounded one the session then ends its turn to wait for; that variant kills the process (`#23`, above). What each exit code and the stdout JSON mean is agent-project-issues' contract (its skill, section "Waiting for CI"); the process decisions on top of it are this plugin's: `2`/`3` repeat the call inside the same round; `4` (or any code outside 0-5) falls back to `list_pipeline_runs` classified by the green condition in agent-project-issues' "Reading a run's `status` and `conclusion`", never to a sleeping poll; a **no-verdict** exit `5` is never green and never a fix round — the first one buys one empty-commit retrigger (an `i` round), the second is `blocked` quoting each run's state and URL, because whether such a run counts is a human decision and a third retrigger would only be a retry. The 45-minute cap per CI round counts as an infrastructure round when hit. The wrapper resolves the CLI by *executing* a candidate (ticket #120, where a bare name that could not run surfaced as rc=126), passes the CLI's stdout/exit through, and maps "no candidate executable" onto exit `4`, so 126/127 never reach the model as a blocker. Both cited sections are verified in the installed `agent-project-issues` 0.3.11; `plugin.json`'s floor is `>=0.2.5`, and an older CLI without `wait-pipeline` is what the exit-4 path and its install hint cover.

## Critic isolation is a property of the process, not of the prompt

`plan-critic` and `test-critic` (`agents/`) are ordinary subagents, but the critique itself runs in separate `claude -p` processes started by `scripts/critic/*-run.sh` with `--setting-sources "" --strict-mcp-config --disable-slash-commands --tools "" --system-prompt <file> --json-schema <file>`, cwd a `mktemp -d` **outside** the repository (CLAUDE.md discovery walks parent directories; a subdirectory of the repo would defeat the isolation). The review package is assembled by a script from verbatim inputs — the ticket transcript, the plan, the test diff — because the curator of a package is the one role that could defang a critique. Since ticket #105, "verbatim" has one narrow exception: the transcript omits comments whose body *starts with* this pipeline's own `<!-- adev:event` marker (`agents/context-extractor.md`). That is a filter on **authorship**, not on relevance — nothing is left out for looking irrelevant, wrong, or inconvenient, only the pipeline's own machine-generated log of an earlier attempt, which carries no requirement a critic could judge against. The merge (`plan-critic-merge.py`) is deterministic code with no model in it: a model between the critics and the decision would be a curator again. `check-critic-isolation.sh` runs as a static pre-flight on every gate invocation; run it with `--live` after every CLI upgrade.

The isolation flag set (`FLAGS` in `check-critic-isolation.sh`) is identical across all four plan-critic lenses and both runners — that is what "isolation" actually means here. `--model` and `--effort` are **not** in that set and are allowed to differ per lens (since #105, `missed`/`misread` run `--effort high`, `untestable`/`simplifier` run `--effort medium` — see "The plan-critic loop converges on a threshold, not on zero" below); varying them changes cost and thoroughness, never isolation. The four lenses' packages are also byte-identical outside the final lens block (PARTs 1-4 — spec, constraints, scope, plan), which is what makes a shared prompt-cache prefix possible in the first place (`plan-critic-run.sh`'s `ADEV_PLAN_CRITIC_CACHE_WARM` switch).

A critic has no repository access. Its claims about existing code are `unverified-assumption` findings, and **`process-developer` never upgrades them to defects** — the planner, which could see the code, is trusted over a critic that could not.

Ported from the `sothis` project's gates (2026-08); the flag set is identical across both runners on purpose, and `check-critic-isolation.sh` refuses to run if one runner drops a flag the other keeps.

## The plan-critic's fourth lens judges mechanism growth, not correctness (ticket #103, revised by #105)

`missed`/`misread`/`untestable` all judge whether the plan is *right*; none of them judges whether it is *bigger than it needs to be*. `lib-python-worktree#148` went through this pipeline clean — plan-critic, test-critic, three review rounds, CI-green — and still landed the fourth patch on the same module in three weeks: a persistent worker, a scan lock, a generation guard, a `GrantedAccess` pre-filter, a deferred-handles cap, two new tags, a new `STOP_REASON`. A plan that adds a 13th constant is *more complete* to `missed`, and *less risky to existing tests* to the reviewer, than one that deletes 8 — the system optimized structurally for accretion. The German ticket text calls the section this closes "Mechanismus-Bilanz"; search for that phrase if you land here from the ticket.

`simplifier` (`plan-critic-package.sh`) is the fourth lens: it holds the plan's mandatory **Mechanism balance** section (`planner.md`) against the rest of the plan — every addition needs a line of justification that survives being asked "why can't this come from removing or reshaping something that already exists", and a plan adding a third mechanism where the specification already names two doing the same job is a major finding. Its `violated_criterion` lives in `plan-critic-constraints.md`'s STRUCTURAL REQUIREMENT bullet, not in the lens text: the merge dedups by byte-exact `violated_criterion`, so putting the criterion in the one part of the package every lens shares is what makes it independently quotable and gives it its own stagnation fingerprint.

**#103 originally built two nets: the `simplifier` lens routed its majors back to the planner unconditionally, and the reviewer checked the balance's `Added` list against the actual diff.** Ticket #105 (`lib-python-worktree#154`: 9 plan-critic rounds, 2 generations, ~4.5h, 0 lines of code) removed the first net and kept the second. The `simplifier` lens (like `untestable`) is now advisory only — its findings are forwarded to the developer as notes, never a reason for another critic round (see "The plan-critic loop converges on a threshold, not on zero" below) — because a critic reading the plan as an isolated document, with no code to check the claim against, reliably found *something* to say about mechanism growth on every round of a large plan, and none of that noise was ever what actually needed fixing on `#154`. The reviewer's "Mechanism balance vs. diff" check stays `[blocking]`: it costs no extra model process, and it judges the plan's `Added` list against the diff that actually landed, not against the critic's guess at what the plan would produce — a stronger check, for free, at the one point in the pipeline where the claim can be verified.

**Deliberately no new `kind` enum value** in `plan-critic-schema.json` for this, and #105 kept that discipline: no new `class` field either — the merge derives a finding's blocking/note status from its `lens`, a fixed table, not a field any critic sets. `kind` drives no routing in `SKILL.md` (severity, now `finding_class`, does) and feeds only the `stagnation-check.py` fingerprint `(kind, violated_criterion)` — a lens free to pick between an old kind and a new one for the same defect would report `gap` in round 1 and the new kind in round 2, reading as *progress* and burning a round for nothing. The existing vocabulary (`gap`/`double-claim`/`contradiction`/`risk`) already covers every case the lens produces, and shipping a new reason code here would be exactly the kind of unjustified addition this ticket exists to stop.

## Round caps are progress-based, not just round-counted (2026-08-25)

plan-critic, test-critic, and review each have a **soft** cap of three rounds and a **hard** cap of six; CI and rebase keep their original hard cap of three, unchanged. `process-developer` counts; a critic never counts its own rounds. An infrastructure-failed round still counts toward the soft cap — exempting it would turn the cap into an unbounded retry loop.

The reason for the split: a fixed round count cannot tell "the same objection dwelling at round 3" from "three genuinely different objections, one per round" — and only the first of those is actually a decision-shaped problem. `agent-ticket-orchestrator#7`/`#8` diagnosed the same confusion one layer up (a retry burned on a case a retry cannot fix); `agent-plugin-dev#21` Problem 2 worked out the fix for this layer, and a live incident (`#99`, `agent-chrome-wrapper` package #42/PR #43 needing 5 review rounds, each with a genuinely new finding) confirmed the diagnosis before this was built.

At the soft cap, `scripts/critic/stagnation-check.py` (deterministic, no model — same philosophy as `plan-critic-merge.py`) compares this round's findings against a per-generation fingerprint history: `(kind, violated_criterion)` for plan-critic/test-critic, `(kind, file, what[:80])` for review (the reviewer has no requirement IDs to quote, see `agents/reviewer.md`'s additive structured findings block). Since ticket #105, the plan-critic/test-critic fingerprint is additionally filtered to `finding_class == "blocking"` — a `simplifier`/`untestable` note is never counted as a fingerprint at all, blocking or otherwise, because a monotonically growing plan produces a *new* note-class finding almost every round by construction, and counting that as "progress" is exactly the false signal that let `lib-python-worktree#154` run to the hard cap on an unchanged critical. A genuinely new **blocking** fingerprint is progress — keep going, up to the hard cap of six. Only fingerprints already seen this generation is stagnation — and stagnation on plan-critic/test-critic/review (never CI, never rebase) triggers **one replan**: a fresh `planner` dispatch with the full findings history inlined, all four gate counters reset, `generation` incremented (capped at 2). Stagnating again at generation 2 is `failed`, with every recurring fingerprint quoted verbatim in the text — full mechanism in `skills/process-developer/SKILL.md`, "Round caps: progress or stagnation" and "Replan".

**A third exit exists alongside clean/stagnation, since #105: acceptance at the soft cap.** With `blocking_severity_counts.critical == 0` (the merge computes this alongside the plain `severity_counts` — see the #103 section above), the plan is accepted at round 3 rather than pushed toward round 6; every still-open major or minor, blocking or note, is forwarded to the developer as a note rather than argued out with another isolated critic round. The stagnation check is now reached only when a *blocking* critical is still open — a plan with no blocking critical has met the bar, and grinding it against `untestable`/`simplifier` noise bought nothing on `#154`.

The reviewer formerly had one fix cycle and no defined path for "still blocking after it"; that gap is closed by the same progress/stagnation logic, not by a bare cap-and-`failed` any more.

## Test-first is two developer dispatches with a gate between them

`phase=tests` writes the driving tests and proves RED; `test-critic` judges whether a wrong implementation would still pass them; `phase=implement` makes them GREEN. The split exists so the critique happens *before* production code biases what the tests are allowed to check.

Since ticket #105, TDD is scoped **per behavioural requirement, by a kind the planner declares**, not per package. `agents/planner.md`'s Test/verification strategy names one of `driving-test` / `existing-suite` / `ci-evidence` / `none` for every requirement, and only `driving-test` requirements get the full RED/GREEN treatment — `untestable` (plan-critic) and `tautology` (test-critic) judge only those. The old rule — a whole package is either behavioural or it skips the gate — is now the special case where every requirement is declared `existing-suite`/`ci-evidence`/`none`; a mixed package (some real code, some config, some docs) runs the gate scoped to its `driving-test` subset, not all-or-nothing. This closes a real cost: forcing a driving test onto every requirement in a package pushed toward manufacturing tests that only assert a literal string is present in a workflow or docs file, which proves nothing a wrong file couldn't also satisfy — `ci-evidence` and `none` exist so that stops being the only available shape.

## Developer and reviewer tool boundaries are denylists

`developer` and `reviewer` use `disallowedTools:` (not `tools:`) so they inherit whatever MCP tools a session connects (Serena, Unity, future servers) while still being blocked from the operations they must never do: the PR/merge/ticket-write MCPs, worktree create/remove, and — for the reviewer — every editing tool. `planner`, `context-extractor`, `plan-critic`, `test-critic` keep an allowlist; they have narrow, known needs. Keep the asymmetry.

## Stack detection lives in the planner and the developer, nowhere else

The planner detects the stack from config files (`pyproject.toml` → `python -m pytest`, `package.json` → `npm test`, `go.mod`, `Cargo.toml`, …) and pins the concrete commands in the plan; the developer runs those (re-deriving if the plan is thin). The skill and the critic scripts are stack-neutral. Project-specific build/test knowledge belongs in a skill of the *target* project, never in this plugin.

## Every git call carries `-C <worktree_path>`

The invoking session's cwd is not pinned to the worktree (`#66`). `process-developer`, `developer`, and `reviewer` all receive `worktree_path` and never issue a bare `git` command. Multi-line commit messages go through `git commit -F <file>`, never a PowerShell here-string via the Bash tool (which runs real bash and would commit a subject of `@`).

## Release payload must ship every `${CLAUDE_PLUGIN_ROOT}`-referenced file (ticket #81)

`release.yml` stages `skills/`, `agents/`, `scripts/` (recursively, so `scripts/critic/` rides along), `hooks/`, `assets/`, `description.md`; `tools/check_plugin_payload.py` scans `skills/**/*.md` and `agents/*.md` for `${CLAUDE_PLUGIN_ROOT}/...` references and fails the build if a referenced file is not staged. The critic runners, schemas, prompts and constraints are referenced from `agents/plan-critic.md` / `agents/test-critic.md` — keep them under `scripts/`.

## The marketplace dispatch payload carries a `changelog` field (ticket #97)

The same notes body `--generate-notes` already produced for the GitHub Release, one step earlier — read back via `gh release view <tag> --json body`, never recomputed a second time so the two can't drift. `agent-marketplace#235` renders it into the opened PR under `## Changelog`; omitted or unrecognised, the field is simply ignored on that side. The whole payload (including the pre-existing `tags` array) is built with `jq -n` rather than spliced into the old unquoted `curl -d @- <<EOF` heredoc — a multi-line changelog containing backticks, quotes or newlines would break that pattern and silently drop the entire dispatch, the same class of bug that already hit this repo's own `tags` field once (`agent-marketplace@89aa850`). There is no `dispatch.yml` in this repo to mirror the change into.

A failed release is never "fixed" in place — "Fail if tag already exists" refuses to reuse a version number, so a failure's only way forward is the next version number. Nothing here tries to detect or special-case a retry, and nothing should.

## Contracts

`release.yml` tags the release itself at a parent-less orphan commit (the marketplace `ref` contract requires that), so it cannot supply its own release-notes history — ticket #107 fixed this by generating notes from `main`'s real history instead, via a parallel `src/<plugin>--v<version>` marker tag pushed at the same commit `main` was at when the run started. That marker scheme carries one one-time manual precondition and one standing dispatch precondition, both enforced by the `Fail if tag already exists` step (`id: preflight`):

- **One-time bootstrap, before the next release runs.** No `src/*` marker exists for any release before this ticket, so the pre-flight's "previous release" check would otherwise fail closed on the very first post-#107 release. Tag the commit the *last* successful `release.yml` run actually built from, and push it, once, by hand:

  ```
  git tag src/<plugin-name>--v<last-released-version> <head_sha_of_that_release_run>
  git push origin src/<plugin-name>--v<last-released-version>
  ```

  Every release after that pushes its own `src/<TAG>` marker automatically (the `Push source tag` step) — this manual step is a one-time gap-fill, not a recurring one. `tools/prev_release_tag.py` resolves "the previous release" by strict-semver order among `<plugin_name>--v*` tags (excluding the tag being created and any `src/*` marker), so the bootstrap only needs the single most recent one; the pre-flight prints the exact two commands above, filled in, whenever it detects a resolvable previous release with a missing marker.
- **Standing precondition: dispatch from the default branch.** The pre-flight aborts if `github.ref_name != github.event.repository.default_branch` — the notes-generation range and the `src/<TAG>` marker are only meaningful relative to that branch's own history, and `workflow_dispatch` does not itself constrain which ref it runs against.

Both preconditions fail before any push, tag, zip, or burned version number — the release either has real history to generate notes from, or it does not run at all.

## Optional Codex review augmentation lives in the reviewer

When the Codex plugin is installed and ready, `agents/reviewer.md` runs `scripts/codex-review.mjs` (read-only, never `--write`) and folds blocking findings into its verdict; every failure degrades silently to the reviewer's own review with a visible `[nit]` so the orchestrator can see the pass did not run. Codex is therefore recommended, **not** declared under `dependencies`. The pass runs on every review round, including re-reviews.

A three-file invariant keeps a Codex-only blocking round from buying a developer fix round or driving the gate to its hard cap and a replan (ticket #112): `agents/reviewer.md` stamps `kind: "codex"` on every Codex-sourced finding in its structured findings block; `scripts/critic/stagnation-check.py`'s `review` gate classifies those as note-class (excluded from the stagnation fingerprint) and reports everything else as `REVIEW_OWN_BLOCKING: <n>`; `skills/process-developer/SKILL.md` Phase 4 reads that count and routes on it — `0` accepts the round and goes straight to Phase 5 (no fix round, no stagnation/replan check), `>0` is today's behavior unchanged. The reviewer's own findings decide what the gate spends; Codex findings ride along to the PR as notes instead.

## The plan-critic loop converges on a threshold, not on zero (ticket #105)

`lib-python-worktree#154` ran `process-developer`'s plan-critic gate for 4.5 hours across 9 rounds and 2 generations and produced zero lines of code, while the plan document grew monotonically (32 KB → 136 KB in generation 1 alone). The diagnosis: an isolated critic with no repository access, reading a large plan as a document, reliably finds *something* on every round — and the pre-#105 contract treated every finding as equally worth another round.

**The fix is a lens → class table, computed once, in one place.** `plan-critic-merge.py` (already model-free — see "Critic isolation" above) derives `finding_class` from the finding's `(lens, severity)` pair: `missed`/`misread` → `"blocking"` at every severity; `simplifier` → `"note"` at every severity; `untestable` → `"blocking"` only when `severity == "critical"`, else `"note"` (ticket #108 — see "A critic-decidable case at the opposite end of #105" below); any lens not named above (including a future lens, and `tautology` from the shared test-critic gate) defaults to `"blocking"` at every severity. This is a fixed table, not a judgment call by a critic or the orchestrator — a critic that could choose its own class would be exactly the curator this pipeline's isolation exists to prevent (see "Critic isolation" above). A merged group's class is the *strongest* class present in the group, not the severity-survivor's own: a `missed` finding and a `simplifier` finding can share a byte-identical `violated_criterion` (the mechanism-balance sentence is exactly this case), and taking anything less than the max would silently declass a real blocker to a note.

Three places had to change together, and missing any one of them reproduces `#154`'s failure mode in a different shape:

1. **`skills/process-developer/SKILL.md` Phase 2** routes only blocking-class findings back to the planner; note-class findings are forwarded verbatim to the developer dispatch instead — cheaper and better-grounded, since the developer checks a note against real code rather than against another isolated critic's blind read of the plan.
2. **`scripts/critic/stagnation-check.py`** filters its fingerprint to `finding_class == "blocking"` before comparing it against the generation's history. Without this, a `simplifier` finding on a growing plan produces a new fingerprint almost every round — `RESULT: progress` — and the loop runs to the hard cap of six on an unchanged critical, which is precisely what happened on `#154`.
3. **Acceptance at the soft cap**: with `blocking_severity_counts.critical == 0` at round 3, the plan is accepted rather than pushed toward round 6, and every open major/minor (blocking or note) is forwarded as a note rather than argued out.

Two more contributors to `#154`'s cost, fixed alongside the above and worth knowing about even though they are not part of the acceptance-threshold mechanism itself: `plan-critic-schema.json` no longer has a `step_assessments` array (a full step-by-step transcript of the plan, required per lens, un-narrowed by the lens, read by no code path in `SKILL.md` — pure output-token cost, quadrupled across four parallel processes); and `agents/planner.md` now states a plan-length budget with a hard non-growth rule on follow-up rounds (a plan that must be re-emitted in full on every round, with no size discipline, is the other half of why the document reached 136 KB).

## A critic-decidable case at the opposite end of #105 (ticket #108)

`#105`'s note-class exists because an isolated critic reading a large plan as a document reliably finds *something* to say about mechanism growth every round, and none of it was ever the actual blocker on `lib-python-worktree#154`. `Seretos/agent-web-tester#20` (fixed by PR #23, reopened as `#25` once the fix shipped) is the mirror-image failure: a first `browser_navigate` call with no cached Playwright browser failed outright; PR #23's driving test asserted only that `src/browser-tool.js`'s source text contained the literal substring `ensureBrowserInstalled(` and that a same-named export existed — never that the call actually installed a browser and completed the navigation on a machine with none cached. The test was green, the ticket's stated symptom stayed exactly as broken as before, and `#25` reopened the same failure a user hit again in the field.

The two cases look identical from a distance — "an isolated critic without codebase access flagged something" — but they are not the same question. Mechanism growth (`simplifier`) is a matter of taste the critic cannot ground against real code: a justified addition and an unjustified one read the same on the page, so treating every finding as blocking just grinds the loop. Whether the ticket's stated runtime symptom is exercised by *any* assertion that actually runs the described behaviour is not a matter of taste — it is decidable from exactly the two documents already in front of the critic at this gate: the plan's `Symptom (verbatim from ticket): "..."` anchor (see `agents/planner.md`) states what must be exercised, and the test diff shows what the assertions actually do. No repository access is needed to tell "this assertion executes the described action" apart from "this assertion only inspects a literal string, a heading, or a JSON key" — that comparison is exactly the `tautology` lens's job at the test-critic gate, and exactly what the plan-critic's `untestable` lens now also checks for symptom coverage declared `none`/`existing-suite`/manual (`agents/plan-critic.md`'s addendum to "never upgrade an unverified assumption to a defect" states this explicitly). That is why `#108` makes this one pattern `critical`-severity `blocking` — at both gates, via the `(lens, severity)` table above — while leaving every other `untestable`/`simplifier` finding exactly as advisory as `#105` made it. A claim about existing code the critic cannot see is still never upgraded; a claim about whether the two documents already in the package cohere is a different question, and this ticket is the one place that distinction is drawn.

## Prose packages are routed elsewhere; the critic gates carry no prose exemption (ticket #126, reverting #123)

`#123` taught both critic gates a `Prose-executed:` exemption (planner declaration, lens/constraint text, a reviewer check backed by `scripts/critic/prose-role-check.py`), because `#122` had deadlocked: a requirement whose only executor is a model reading a prose file drew critical `tautology` when declared `driving-test` and critical `untestable` (#108) when declared manual. That deadlock is now solved one layer up instead: prose work has its own lower plugin (`agent-autonomous-prompt-engineer`, entry `process-prompt-engineer`) and the upper layer routes packages by lane, so this pipeline only ever sees code packages. `#126` therefore removed the exemption whole — every exemption is a way for a *code* package to slip past `untestable`/`tautology`, and this one no longer had a case to serve. The #108 rule is back to its unexempted form. **Do not re-add a prose carve-out here**; a prose package arriving in this pipeline is a routing bug upstream, and `blocked` is the correct outcome. What stayed from `#123` because it is not prose-specific: Phase 5's `## Not covered by tests` PR section, which lists every `none`/`ci-evidence` requirement — both kinds remain legitimate for code (`#105`).

## Doc-prose tests are a mechanical contract, not a wording pin

This repo's own test suite (`tests/`) is mostly text-parsing against `agents/*.md`, `skills/*/SKILL.md` and this file — there is very little executable code here to test any other way, and that is fine. But a text-parsing test earns its place only when *something else reads the string mechanically*: the harness parses `tools:`/`disallowedTools:` frontmatter, `check-critic-isolation.sh` greps the six isolation flags, `plan-critic-merge.py` dedups on a byte-exact `violated_criterion`, GitHub Actions parses `release.yml`. A test that only asserts a human-facing sentence contains a particular phrase — "the plan must say `14 days`", "the word `simplification` must appear" — is not that; it is a rewording tax; it makes every improvement to the prose a red build regardless of whether the rule it describes changed, and rewards leaving the old wording in place and adding a new paragraph next to it over actually rewriting it. That is the same accretion failure mode ticket #105 exists to fix, just at the level of this repo's own documentation instead of a target project's plan.

Ticket #105 removed three such tests from `tests/test_mechanism_balance.py` (mechanism-balance section headers, "repeat fix"/"14 days"/"simplification", a bare `recent_changes` substring) for exactly this reason, and kept everything that gates a real cross-file contract: the closed 13-event vocabulary, the isolation flag set, the `kind` enum, the frontmatter tool lists, the JSON schemas, the release workflow's actual YAML. When adding a new doc-prose test, ask what reads the string besides a human — if the answer is "nothing", it likely doesn't belong here.

## Provider-portability gotchas

This plugin does not restate provider vocabulary; it cites agent-project-issues, which owns it. The PR closing syntax per provider is its skill's section "Pull requests: closing the ticket on merge"; the run vocabulary and the green condition are its section "Reading a run's `status` and `conclusion`" (both verified in 0.3.11). Ticket #128 applied this to the code (PR #132: README, `scripts/ci-promised-check.py`), #130 to the three prose files (`skills/process-developer/SKILL.md`, `agents/developer.md`, this file). Two GitHub-specific spots remain on purpose: Phase 5's PR-body cap (60000 against GitHub's 65536, kept until upstream pre-validation — agent-project-issues#364 — ships in a released version) and `ci-promised-check.py`'s `.github/workflows/` scope (a #128 non-goal).
